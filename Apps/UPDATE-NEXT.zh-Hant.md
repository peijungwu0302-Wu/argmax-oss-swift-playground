# 維護中：SenseVoice 音訊接縫、錄後重轉錄與純字幕

本次基底是 `playground-compatible / eba94a0`，開始時工作目錄乾淨。以下是尚未發布的原始碼修改；既有公開 IPA 仍是 1.5.0 build 10，不含本次變更。Bundle ID 保持 `com.peijungwu0302.lecturetranscriber`。

## 約 12 秒漏句的檢查結果

- 舊路徑每次讀取最多 192,000 個 16 kHz 樣本，定稿後將游標推進實際切段長度。下一輪從游標開始，沒有重疊上下文；沒有找到「固定跳過句尾樣本」的游標運算。
- `StoredAudio.read` 的 PCM 讀取會補足要求長度，不足就報錯；錄音 tap 先寫入檔案再增加樣本計數。這是原始碼檢查，不代表真機麥克風、背景與取樣轉換已證明毫無遺失。
- 原本 `hasSpeech == false` 的音量判斷會直接略過模型，但仍推進音訊游標。低音量語音有被誤當靜音的風險；新版停頓判斷只用於選切點，全部所選音訊都送入模型。因此安靜時的推論量也可能增加。
- 模型會複製全部前處理特徵並填入實際 `speech_lengths`；找不到可容納的尺寸會報錯。原本解碼使用 `min(frames + 4, logits 長度)`，改為長度不足就報錯，不再默默接受截短輸出。目前沒有證據顯示你那次漏句曾觸發尺寸不符。

## 本次 SenseVoice 流程

即時辨識從已保存檔案讀取有前後文的視窗，保留末端音訊供下一輪更新；遇到停頓或視窗上限才定稿。切點前的音訊會在下一輪重新讀取。游標只推進本段負責的範圍，前後重疊音訊不重複計入時間；定稿及游標成功存檔後才更新記憶體進度。

初始工程設定是前後各最多 1 秒、單次模型輸入仍不超過 12 秒；連續語音的中間視窗通常負責 10 秒。這些是待驗證的程式參數，不是實測最佳值，也不是端到端延遲承諾。

接縫文字依 CTC emission frame 選取，使用模型前端的 10 ms frame hop、LFR stride 6 與四個前置 query frames；不以字數猜時間，也不以相同字串刪除重複句。UTF-8 byte fallback 序列保持完整。模型結構參考 [FluidAudio SenseVoice 文件](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/SenseVoice.md)。

**CTC emission 位置不是經驗證的逐字時間戳。** 同一個字在不同視窗的 emission 可能移動，所以跨窗仍可能重複或漏字。這次加入音訊上下文與錄後重跑，還沒有完成多輪假說比對後的穩定文字演算法、強制對齊或全課堂的全局接縫校正。不能將「音訊有完整涵蓋」等同「文字 100% 完整」。設定的辨識狀態顯示最近一次模型輸入、本段、前文及後文的樣本數，方便真機排查。

## 錄音後重新產生逐字稿

停止錄音後，在「錄音設定」或「匯出」選擇 **SenseVoice 重新轉錄（另存新課堂）**。

1. 複製整堂課所有已有音訊片段，保留片段時間、標記、來源語言；建立獨立的新課堂。
2. 從每個片段開頭重新用 SenseVoice 辨識，包括先前已定稿的部分。已有 AAC 會解碼辨識，不會恢復成壓縮前的音質。
3. 新逐字稿與翻譯另存；原課堂的錄音、逐字稿、使用者修改、翻譯和會議紀錄都留在原課堂。新稿不會沿用舊會議紀錄。
4. 若辨識或模型下載中斷，新課堂保留待處理進度，可以「補辨識」接續；若建立副本失敗則清理未完成副本。需要額外磁碟空間，長課堂請保持前景。

原本的「補辨識」仍只補未處理音訊；新入口才是整堂重跑。錄後第二遍沿用相同模型和上下文切段，不做 AI 改寫或推測補句，也不保證每一段都比第一遍準確。

## 字級與 Slide Over

「錄音設定 → 文字大小」可分別調整原文字幕、中文翻譯、逐字稿，存到裝置上。精簡模式隱藏 App 自己的導覽列、課堂標題、計時、說明和底部按鈕；保留原文／翻譯及右上角 `…` 控制選單，可返回完整畫面、開設定或停止錄音。字幕不再為塞進固定行數而自動縮小字級，精簡模式可捲動。

Apple 的 [iPadOS 26 多工說明](https://support.apple.com/en-us/125309) 支援 Slide Over 視窗並可用下角把手調整大小。請先在系統「多工與手勢」選用 Windowed Apps，再從 App 視窗控制進入 Slide Over。

App 的導覽列可隱藏；iPadOS／Swift Playgrounds 管理的視窗上緣和最小尺寸，無法靠移除 App 內工具列就消失。這版尚未實作 PiP，不能宣稱可縮成 Windows Chrome 那種無框跨 App 字幕條。PiP 是後續需獨立驗證的方向，包含系統控制、背景辨識／翻譯和耗電；不是開一個選項便能把任意 SwiftUI 畫面浮到其他 App 上。

## 驗證與一次完成的真機檢查

Windows 已完成 Swift 語法解析與 `git diff --check`。本機沒有 Swift／Xcode，新增的 Swift 行為測試、Core ML 接縫測試及 UI 測試尚未執行；舊版雲端成功紀錄不能當作本次測試結果。本次沒有產出或替換 IPA。

已補測試案例：完整樣本範圍涵蓋、低音量與極短尾段、重疊範圍、CTC 重複詞與 UTF-8、重轉錄副本與原修改保留、真實模型同一視窗兩側輸出的完整性，以及精簡畫面／字級入口。真實跨窗準確率仍須同一音訊比較，不能由單一視窗的 CTC 分區測試推論。

新版本完成雲端編譯後，真機請一次做：

1. 用同一段至少 60 秒的中英混說音訊，刻意讓完整句子跨過 10／12／20／24 秒，末尾也保留可辨認的詞；錄完先播放確認原音是否完整。
2. 修改原課堂一行文字，再另存重新轉錄；比對兩份逐字稿的接縫與末句，確認原修改、標記與錄音仍在。記錄重跑耗時，不預設延遲目標。
3. 開精簡字幕與 Goodnotes 並用，調整三種字級，測 `…` 返回／停止；再將視窗移出畫面後返回，檢查音訊與補辨識。完全進入背景仍依原設計先存錄音，返回後才補辨識／翻譯。
